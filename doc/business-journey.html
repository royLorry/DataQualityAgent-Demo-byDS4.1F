背景 · 诉求 · 本文档定位

从「数据质量标准管理系统」的人工协作痛点，到数据质量 Agent 的两大业务旅程。

现有系统管理着结构化和多模态的数据质量标准（Standard）、数据质量规则（Rule）、数据质量探针（Probe）。三个痛点驱动本项目：标准依赖人工制定；标准到可执行规则、再到可运行探针，依赖业务人员与开发人员反复沟通协作；开发耗时长。

数据质量 Agent 的诉求：从规则出发，通过数据本体 / 数据血缘系统查找关系，实现 SQL 探针与 Python 脚本探针的 AI 编写，落地为可运行的探针，并实现探针调度运行。

系统目标一句话：让业务人员用自然语言编排 Agent，让 Agent 借助本体/血缘与 LLM 自动把规则翻译成可运行探针，并调度执行、闭环回写。
本文档是三份交付物之一的业务旅程设计文档，全部内容严格对齐统一设计规范（Single Source of Truth）；实体命名、枚举值、流程顺序、原则表述与规范逐字一致。姊妹文档：架构设计文档（architecture.html）。
01

设计原则

五条原则（P1–P5）是两大业务旅程的最高约束：旅程中的任何一步若与原则冲突，即评审不通过。

需求 REQ业务编排与 IT 实现必须解耦，所有设计决策受统一原则约束，避免「业务需求排队等开发」的协作返工。
设计 DESIGN以规范 §1.2 五条原则为顶层约束，逐条给出旅程落点与理由；三层结构（L3 用户自编排层 / L2 通用执行引擎层 / L1 持久化层）是原则的架构表达。
验收口径 ACC五条原则逐字保留；每条含设计理由与「为什么重要」；后文章节（旅程步骤、组件映射、情绪干预）可反向引用对应原则编号。
P1

业务活动用户自编排

Agent/Task/Skill/Tool 的编排是用户（业务人员）的活动，不是开发者写死的代码。

设计理由：配置态旅程（第 03 章 C1–C4）的四个步骤全部发生在 L3 用户自编排层的向导界面里，开发者只负责提供 Tool 接入网关，不编写任何具体业务活动的代码。业务活动的定义以数据形态沉淀在 agent/task/skill 实体中，而非源码。

为什么重要业务变更不再走「提需求、排期、发版」循环；新增一个业务活动的时间从开发周级压缩到配置小时级，这是本项目的核心收益。
P2

业务数据持久化由 Tool 调用，不是 Agent 数据

Agent 不直接把业务数据当自己的记忆/状态；落库一律通过 Tool 原子调用。

设计理由：Agent 的 Message Context 与 Execution Context 只承载过程数据；探针落库必须经 probe.upsert，知识获取必须经 knowledge.load，禁止知识直连数据库。业务数据的真源永远是 L1 持久化层的数据表。

为什么重要保证审计可追溯（每次写入都有 trace 记录）、权限可按租户收敛、LLM 可替换而业务数据零丢失：模型是算力，不是账本。
P3

规则/探针是业务产出物

规则与探针是一等业务资产，可版本化、可审计、可复用。

设计理由：rule 与 probe 是数据模型中的一等实体，探针携带状态枚举 DRAFT → RUNNABLE → SCHEDULED、类型 SQL/PYTHON 与数据源绑定；运行态旅程的终点产出物（第 06 章 S1–S5）全部以资产形态入库，而不是聊天记录。

为什么重要业务投入被资产化保护：探针可被后续需求复用、按维度（完整性/准确性/一致性/及时性/唯一性/有效性）组合治理，边际成本递减。
P4

执行器用现成工具

执行引擎不重复造轮子，复用 LangGraph/LangChain 生态与既有调度器。

设计理由：L2 通用执行引擎层的 DAG 骨架直接采用 LangGraph StateGraph；HITL 用 interrupt() 与 Command(resume=...)；消息压缩复用 LangChain trim_messages/SummarizationMiddleware；探针调度复用 APScheduler/Celery Beat。

为什么重要把工程资源集中在领域差异化能力（规则到探针的翻译、本体/血缘联动）上，通用编排问题交给成熟生态，降低长期维护风险。
P5

知识加载是 Planner 的职责

知识不是全局塞进上下文，而是在规划阶段由 Planner 按 Task 白名单按需加载。

设计理由：运行态旅程 R3 知识加载步骤由 Planner 在规划阶段执行，可见范围按「租户 → Agent → Task」三层白名单收敛，Knowledge Context 的生命周期是节点级、随规划生灭，而不是会话级常驻。

为什么重要直接决定 token 成本、答案确定性与多租户隔离：无关知识不进上下文，越权知识不进候选池，上下文窗口留给真正参与决策的证据。
02

旅程总览

两大旅程以「发布」为交接点：配置态的产出物 Agent.status = PUBLISHED，是运行态的 Config Context 输入。

需求 REQ读者必须在一屏之内分清：谁在什么条件下触发哪条旅程、涉及三层架构的哪些层、最终得到什么。
设计 DESIGN先给出资产层级（旅程操作的对象），再以双链路总览图 + 触发条件/参与角色/涉及层级/关键产出四维对比表呈现。
验收口径 ACC两条链路的节点顺序与规范 §3 严格一致（配置态 4 步 + 前置；运行态 7 步）；对比表四行齐全；层级关系基数为 1:N。

2.1 资产层级关系（旅程操作的对象）

  • Agent业务活动
    • Task子业务活动1:N
      • KnowledgeTask 维度知识白名单（允许加载的知识）1:N
      • Skill能力包1:N
        • Tool原子能力【内置】+【开放注册】1:N
    • KnowledgeAgent 维度知识白名单（允许加载的知识）1:N
基数口径：父 → 1:N → 子。一个 Agent 含 N 个 Task；一个 Task 含 N 个 Skill；一个 Skill 含 N 个 Tool；Agent 与 Task 各自可挂 N 个 Knowledge。Tool 分【内置】与【开放注册】两类。

2.3 双旅程对比

维度配置态 Journey（Configuration）运行态 Journey（Runtime）
触发条件 用户开租（Tenant Provisioning）后进行；业务需要新增/变更业务活动，或开发者接入新原子能力时。 业务用户发起需求后触发（自然语言）；或由定时调度触发既有业务旅程（如 S4 探针批量调度）。
参与角色 主导：业务用户、开发人员（Tool 注册）；配合：数据质量管理员（知识权限）、数据工程师（数据源/血缘就绪）。 主导：业务用户（发起 + HITL 确认）、Agent Runtime（路由/规划/执行/判定）；配合：数据质量管理员（审核探针）。
涉及层级 L3 用户自编排层为主，产出物落入 L1 持久化层（agent/task/skill/tool/knowledge 表）。 L2 通用执行引擎层为主（Router/Planner/Executor/Gate），前台呈现于 L3，产出物回写 L1。
关键产出 Agent.status = PUBLISHED 的可执行业务旅程 + Tool/Skill/Task/Knowledge 资产链。 可运行探针（SQL/PYTHON，DRAFT → RUNNABLE → SCHEDULED）、调度计划、运行报告（ProbeRun）、审核记录、链路追踪 Trace。
交接契约：配置态以 PUBLISHED 状态收口，运行态以该状态的 Agent 定义作为 Config Context（租户级、长驻）读取入口。配置态改动在下一次运行态规划时生效，运行态不回写配置态资产定义（只回写业务数据，符合 P2/P3）。
03

旅程详细设计

每一步定义五元组：输入 / 动作 / 输出 / 负责组件 / 失败回退，保证旅程可执行、可追踪、可回退。

需求 REQ旅程不能停在口号级：每一步必须能回答「拿什么、做什么、产出什么、谁执行、错了怎么办」。
设计 DESIGN配置态含前置共 5 步（C0–C4），运行态 7 步（R1–R7）；步骤顺序与规范 §3 主链路严格一致，产出物命名对齐数据模型实体与枚举。
验收口径 ACC12 个步骤五元组均非空；Gate/Finish 必须同时覆盖 LLM 判断与人工确认（HITL）双路径；意图分类落在 8 个固定枚举值内；失败回退不含「未定义」。

3.1 配置态 Journey：Tool 注册 → Skill 编写 → Task 配置 → Agent 编排

C0

前置 · 开租后自动加载

数据工程师 · 系统
输入
租户开租（Tenant Provisioning）完成：tenant.status 置就绪、provisioned_at 落库。
动作
数据源与知识体系通过本体服务自动加载：同步 Datasource 与 Knowledge（类型 ONTOLOGY/LINEAGE/RULE/STANDARD/DOC）；平台注入 10 个内置 Tool（ontology.lookup、lineage.query、knowledge.load、sql.execute、python.run、probe.upsert、probe.schedule、datasource.list、standard.list、rule.list）。
输出
数据源清单就绪、知识候选池就绪、内置 Tool 可用，配置态工作台开放。
负责组件
L3 开租向导 → L1 datasource/knowledge/tool 表；本体/血缘为外部系统对接。
失败回退
局部同步失败：租户进入「降级就绪」（可见已加载部分），告警数据工程师手工触发重同步；不阻塞 Tool 注册步骤。
↓ 产出物：Tool 目录（供 C2 组合）
C1

Tool 注册

开发人员
输入
内置能力勾选清单 + 外接 API 的 OpenAPI/Schema 定义（名称、类别、入参出参、鉴权方式、限流阈值）。
动作
注册内置/外接原子能力：外接 Tool 经 tool.register 网关接入，校验 schema_json，绑定鉴权、限流、版本；类别置 BUILTIN/REGISTERED，类型 kind = KNOWLEDGE/SQL/PYTHON/QUERY/IO。
输出
可被 Skill 引用的 Tool 实体（含完整 schema 与调用约束）。
负责组件
L3 Config Workbench Tool 页 → L2 tool.register 网关校验 → L1 tool 表。
失败回退
schema/鉴权校验不过：保存为草稿并高亮失败原因，不进入可用目录；已注册 Tool 联调失败：下线并通知所有引用它的 Skill（级联检查）。
↓ 产出物：Tool 集合（供 C2 组合成能力包）
C2

Skill 编写

业务用户 （Developer 协办）
输入
一个已选定的 Task 上下文 + 候选 Tool 集 + Prompt 编写需求。
动作
选择一个 Task 上下文，组合多个 Tool + Prompt 模板形成能力包；配置渐进披露层级：L0 元数据（name/description，用于路由与选择）、L1 摘要（能力说明 + 所需 Tool 列表）、L2 完整（Prompt 模板 + Tool schema + 示例）。默认只注入 L0，命中后逐级展开，节省上下文。
输出
Skill（含 prompt_template、disclosure_level）与 SkillTool 关联。
负责组件
L3 Skill 向导 → L1 skill/skill_tool 表；披露注入器位于 L2 执行期生效。
失败回退
Prompt 试运行不过或引用了未注册 Tool：发布校验拦截，定位缺失项并回到编辑态；已发布 Skill 的底层 Tool 变更时标记「待复核」。
↓ 产出物：Skill 能力包（供 C3 绑定）
C3

Task 配置

业务用户 （DQ Admin 会签知识）
输入
子业务活动目标描述 + 可用 Skill 集 + 知识白名单候选（受租户权限收敛）。
动作
定义子业务活动目标（goal）与顺序（order_index）；绑定 Skill；绑定知识白名单（TaskKnowledge）；设置 Gate 判定策略：LLM（模型判定）、HUMAN（人工确认）、BOTH（模型初判 + 人工复核）。
输出
Task 实体（含 gate_policy）与 task_knowledge 关联；Gate 策略交由运行态消费。
负责组件
L3 Task 配置页 → L1 task/task_knowledge 表；L2 Gate 策略引擎读取配置。
失败回退
白名单内知识权限校验不通过：退回数据质量管理员走 knowledge.grant 授权流程；Skill/知识缺绑：发布校验失败，Agent 保持 DRAFT。
↓ 产出物：Task 序列 + Gate 策略（供 C4 编排）
C4

Agent 编排与发布

业务用户
输入
业务活动目标 + Task 引用集 + Agent 维度知识白名单。
动作
定义业务活动（business_activity）与描述；引用已配置 Task；绑定 Agent 级 Knowledge；发布为可运行的业务旅程。
输出
Agent.status = PUBLISHED。配置态完成标志：一个可执行的业务旅程被发布。
负责组件
L3 Agent 编排画布/发布按钮 → L1 agent 表 → 发布后作为 L2 的 Config Context（租户级、长驻）。
失败回退
引用的任一 Task 未就绪：发布拦截并列出缺失清单；发布失败保持 DRAFT，可修订后增量重试；已发布 Agent 的变更走新版本，旧版本继续服务在途任务。

3.2 运行态 Journey：用户发起需求 → 路由匹配 → 知识加载 → 规划子活动 → 执行子活动 → 子活动 Gate 判定 → 任务 Finish 判断

R1

用户发起需求

业务用户 → Agent Runtime
输入
自然语言需求。端到端剧本样例：「帮我给订单表 order 的主键 order_id 生成一个非空校验探针，并每天凌晨调度运行。」
动作
创建会话；消息以 Message(role=USER, zone=HOT) 落库进入三层消息分区（HOT/WARM/COLD），构成 Message Context（会话级、可压缩）。
输出
用户消息 + 会话上下文，进入路由入口。
负责组件
L3 运行态工作台输入区 → L1 message 表 → L2 主干入口。
失败回退
落库失败：本地暂存队列重试；输入为空或语义不明：不进入执行链路，转 FOLLOW_UP 意图追问。
↓
R2

路由匹配（三层 Router）

Agent Runtime
输入
用户消息 + 当前状态（是否等待 HITL、是否有在途任务）。
动作
三层顺序执行：Stage1 状态检测（State Detection）：判断当前处于配置态/运行态、是否等待 HITL、是否可继续，输出状态标签；Stage2 意图分类（Intent Classification）：把消息分类到固定意图枚举（CONFIG_TOOLCONFIG_SKILLCONFIG_TASKCONFIG_AGENTRUN_PROBE_REQUESTQUERY_RESULTFOLLOW_UPHITL_RESUME）；Stage3 动作执行（Action Execution）：按意图 + 状态把请求路由到对应 DAG 子图/节点/工具链。剧本消息命中 RUN_PROBE_REQUEST。
输出
状态标签 + 意图类别 + 动作路由目标。
负责组件
L2 DAG 节点 router_stage1_state → router_stage2_intent → router_stage3_action；配置上下文（路由规则）来自 L1。
失败回退
意图置信度低：降级为 FOLLOW_UP 澄清式追问；状态冲突（在途任务 + 新请求）：询问用户排队或并行，绝不静默丢意图。
↓
R3

知识加载（Planner 职责）

Agent Runtime · 权限：DQ Admin 预授
输入
Task/Agent 知识白名单；可见范围按「租户 → Agent → Task」三层收敛，无权限知识不进候选池。
动作
由 Planner 在规划阶段决定加载哪些、加载多少（P5）；经权限校验后统一通过 knowledge.load Tool 拉取（不直连数据库，P2）；每个知识片段携带来源与权限标记。剧本中加载「本体/血缘/规则」三类知识。
输出
Knowledge Context（节点级，随规划生灭）：命中的 Standard/Rule 定义、order.order_id 实体属性、上下游血缘。
负责组件
L2 DAG 节点 knowledge_load（Planner）→ L1 knowledge 表 + knowledge.load 原子 Tool。
失败回退
拉取超时：重试一次后降级为空加载，并在规划说明中显式标注「知识缺口」，避免模型凭空假设；权限拒绝：提示走 knowledge.grant 申请。
↓
R4

规划子活动（产出 DAG 骨架）

Agent Runtime（Planner）
输入
意图 + Knowledge Context + Config Context（Agent/Task/Skill/Tool 定义、Gate 策略）。
动作
Planner 产出子活动（Task）序列 = DAG 骨架；初始化 Execution Context（DAG 状态、当前节点、变量、重试计数，任务级）。
输出
可执行 DAG。剧本规划：定位字段 → 生成 SQL 探针 生成 Python 校验 落库 调度
负责组件
L2 节点 plan_subtasks（LangGraph StateGraph，State 为 TypedDict，含 messages/execution/knowledge/config）；Checkpointer 持久化（原型 MemorySaver / 生产 PostgresSaver）。
失败回退
规划发散或成环：回退到该 Agent 的模板 DAG；仍失败则 interrupt() 转人工编辑计划，用户确认后才继续。
↓
R5

执行子活动（ReAct 循环）

Agent Runtime（Executor）
输入
DAG 当前节点 + 节点所需 Skill（按渐进披露 L0→L1→L2 展开）+ 四类上下文。
动作
Executor 以 ReAct 循环（Thought → Action → Observation）执行，调用 Skill→Tool；剧本依次触达 ontology.lookup、lineage.query、sql.execute、python.run、probe.upsert、probe.schedule。每次 LLM 调用（model/token/耗时/节点名）与 Tool 调用（入参/出参/耗时/状态/错误）写 Trace，前台 Trace 面板时间轴可视化。
输出
节点产出物：SQL 探针与 Python 校验脚本草稿（Probe.status = DRAFT，type SQL/PYTHON）、落库结果、调度计划草案、Trace 时间轴。
负责组件
L2 节点 execute_subtask（ReAct loop）→ L1 原子 Tools；业务数据落库一律经 Tool（P2）。
失败回退
Tool 报错：Execution Context 重试计数递增，按策略重试；重试耗尽：节点失败并把错误证据交给 R6 判定，由 Gate 决定回炉执行、回炉规划或转 HITL 人工。错误不伪装成功。
↓ 未通过则回 R5 / R4（循环）
R6

子活动 Gate 判定（LLM 判断 / 人工确认 HITL）

Agent Runtime + 业务用户
输入
子活动产出物 + 验收口径（来自加载的 Standard/Rule 知识）+ Task 的 gate_policy（LLM/HUMAN/BOTH）。
动作
每个子活动结束做 Gate，分两种：LLM 判断：模型对照验收口径输出通过/不通过 + 理由；人工确认（HITL）：引擎执行 interrupt() 暂停，前台弹出 Gate 判定卡（含 LLM 理由供参考），业务用户确认后以 Command(resume=...) 恢复 DAG 继续执行。剧本设计为一处人工确认（落库前）。
输出
判定结果：通过 → 前进下一子活动；不通过 → 回 execute_subtask 重试或回 plan_subtasks 调整；人工拒绝 → 终止并留痕。判定与确认人写入 trace/审核记录。
负责组件
L2 节点 gate_subtask（LLM 评估器 + HITL 中断）→ L3 Gate 判定卡（确认/驳回按钮）→ L1 trace。
失败回退
LLM 判定置信度不足：强制升级人工（BOTH 语义兜底）；人工超时未确认：任务挂起等待 HITL_RESUME 意图恢复，状态由 Checkpointer 保存、不丢进度。
↓ 全部子活动通过后
R7

任务 Finish 判断（LLM 判断 / 人工确认）

Agent Runtime + 业务用户
输入
全部子活动的通过状态 + Agent 级整体目标达成度。
动作
全部子活动通过后判断整体任务是否 Finish，同样分 LLM 判断 与 人工确认 两种路径；Finish 触发第 ⑤ 号消息压缩时机（Hot 原文 → Warm 摘要 → Cold 归档嵌入）。
输出
Finish 通过 → END。终态产出物：探针（SQL + PYTHON，status = SCHEDULED）、每天凌晨的调度计划、运行报告（ProbeRun）、审核记录；前台展示生成的探针与调度计划。
负责组件
L2 节点 finish_check → L1 probe/probe_run/trace 持久化 → L3 结果视图与资产列表。
失败回退
整体未达成：回到执行/规划补齐未通过子活动；人工否决：终止本次运行，产出「中止报告」并保留全部过程证据，可修订需求后重新发起。
DAG 主干对照（规范 §6）：router_stage1_state → router_stage2_intent → router_stage3_action → knowledge_load (Planner) → plan_subtasks → execute_subtask (ReAct loop) → gate_subtask (LLM/HITL) ⇄ 循环 → finish_check (LLM/HITL) → END。

07

用户情绪曲线

情绪值域：-2 焦虑 ↔ +2 愉悦。曲线横跨配置态与运行态的 10 个关键节点，每个负向节点必须对应一个设计干预机制。

需求 REQ旅程质量不只是流程正确，还要体验可预期：识别断点（低谷）并前置设计兜底，避免用户在焦虑点流失。
设计 DESIGN按规范 §13 十节点取值绘制 SVG 折线图（y 轴 -2 到 +2），标注情绪语义与设计干预；配置态/运行态分区着色。
验收口径 ACC10 个节点的数值与语义与 §13 逐一对应（+1/-1/0/+2/-1/+1/+1/-2/0/+2）；每个 ≤0 的节点有对应机制说明；曲线可离线打开。
● 正向（+1 / +2） ● 中性（0） ● 负向（-1 / -2）

解读与设计干预

曲线呈「双峰两谷」形态：配置态以 Agent 发布成功（+2，成就感） 收束，运行态以 探针生成 + 调度成功（+2，价值兑现） 收束，两个峰值正是 P1（用户自编排）与 P3（规则/探针是业务产出物）的价值时刻。中间的下坠是旅程设计的重点防线：

-1 技术门槛
Tool 注册繁琐是开租后的第一道坎。干预：内置 Tool 目录预置可勾选、OpenAPI 导入自动生成 schema、注册即时联通性自检，把「写代码」降为「做选择」。
-1 不确定
发起需求后的等待最容易被误判为「没反应」。干预：路由命中卡片与知识加载卡片即时回显（来源、权限标记、Tool 名），Trace 面板时间轴持续滚动，等待全程可观测。
-2 焦虑谷
执行中报错/重试是全旅程最低点。干预：错误原样呈现不伪装成功、重试计数与退避策略可见、失败自动升级 Gate 转 HITL；用户随时可接管，焦虑被「可修复 + 可接管」双保险承接。
0 掌控感
Gate 人工确认介入把曲线从谷底拉回中性：确认权在人手里，是信任的回稳点而非打扰点，其后直挂 +2 的价值兑现。
验收基线：负向节点（-1 / -2）共三个，均已有对应产品机制；任何后续旅程改版不得新增「无机制承接」的负向节点。
